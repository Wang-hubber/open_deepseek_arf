# ARF v1.x 架构设计

> 从第一轮"具体→抽象→具体"的踩坑中提炼的更干净抽象。
> 当前状态：设计草案，尚未实现。

---

## 架构约束：零黑障

对开发者和调试者，**一切都是透明的，有迹可循的**。Bus 上发生的一切公开可见——没有隐式状态转换，没有静默失败，没有"不知道发生了什么"。

以下事件全部以消息形式流经 Bus，天然可 trace、可 debug、可回放：

- 节点上线/下线/心跳
- task 创建/阻塞/唤醒/失败/级联释放
- model_call 发出/返回
- tool call 请求/result 返回
- peer message 发送/接收

---

## 六要素

```
┌─────────┐  ┌─────────┐  ┌─────────┐
│ Agent A │  │ Agent B │  │ Agent C │
│ Engine  │  │ Engine  │  │ Engine  │
│ State   │  │ State   │  │ State   │
└────┬────┘  └────┬────┘  └────┬────┘
     │            │            │
     └────────────┼────────────┘
                  │  J-RPC / CAN 广播模式
     ┌────────────┼────────────┐
     │            │            │
┌────┴────┐  ┌────┴────┐  ┌────┴────┐
│  MCP    │  │ Model   │  │ 其他     │
│  资源    │  │ Adapter │  │ Consumer │
│  管理器  │  │         │  │          │
└─────────┘  └─────────┘  └─────────┘
```

一条 Bus + 五类节点。Engine 读取 AgentConfig 做资源发现，MCP 不感知 Agent——全部通过消息契约耦合。

---

### 1. Bus — 消息总线

**J-RPC 广播模式**，所有节点挂在同一条总线上。

**消息格式：**
```
{id, type, from, to?, payload}
```
- `to` 为空 = 广播
- `to` 指定 = 定向（指定消费者消费后 drain）

**在线节点图：** Bus 自身维护一张当前在线节点图，节点通过以下报文交互：

- `node_online{type, capabilities...}` — 上线广播，携带节点类型和能力声明
- `node_offline` — 下线广播
- `heartbeat` — 周期性心跳，超时未回复自动标记 offline

其他节点随时通过听广播 + 查看在线节点图，知道当前有哪些节点在线、各自有什么能力。节点的 discover 不是主动查询，是**听广播 + 看图**，零延迟。

**节点离线处理：** 节点离线 → Bus 广播 `node_offline` → Engine 收到后沿该节点相关的 task 依赖链级联释放 → Agent 收到显式的"节点离线，task 无法继续"通知。不是静默挂起。

---

### 2. AgentConfig — 声明式配置骨架

**纯数据结构，声明"我需要什么"。** Agent 的概念就是一个 struct——AgentConfig 描述一个 agent 需要的全部资源，全部使用逻辑名，不感知 Bus。

- **system_prompt** — 系统提示词
- **models** — `Vec<ModelSpec>`，按优先级排列。每个 ModelSpec 声明 provider / model_name / thinking_enabled / temperature / max_output_tokens
- **tools** — `Vec<ToolSpec>`，每个声明 name / permission (Allow/Ask/Deny) / parameter_filter / JSON Schema
- **allowed_paths** — 沙箱允许的路径白名单
- **subagents** — `Vec<ResourceSpec>`，声明 "我需要什么样的 subagent"（node_type + capabilities 匹配条件），1:N 映射
- **teammates** — `Vec<ResourceSpec>`，同上

AgentConfig **不知道** Bus 的存在，不知道 MCP 的存在，不知道节点是否在线。它只是数据——Engine 负责解析和驱动。

---

### 3. Engine — 状态机转移引擎

**职责：发现资源 → 收消息 → 调模型 → 得 action → 发消息。** Engine 拿 AgentConfig 的声明式配置，连上 Bus 后做资源发现，将逻辑名解析为 NodeId，然后驱动 ReAct 循环。

**init 阶段：**
- 读取 AgentConfig，连接 Bus
- 发 discovery 广播，收集匹配的 model/MCP/subagent/teammate 节点
- 将 1 个 ResourceSpec 解析为 N 个 NodeId，全部注册到 ResolvedManifest
- 运行时选第一个在线的节点使用

**ReAct 循环：**
- 监听 Bus 上的消息，按 session_id 过滤归属
- 调用 ModelAdapter（通过 Bus 发 `model_call` 消息）
- 收到模型返回的 action 决策后，通过 Bus 发 `action` 消息
- **不直接调用 MCP**，不直接调用工具——所有执行指令都通过 Bus

**中断与恢复：**
- 收到 `interrupt` 消息 → park，State 持久化
- 收到 `resume` 消息 → 从 State 恢复，继续运行

**State 管理：**
- State 持久化、加载、恢复由 Engine 统一管理

---

### 4. State — 状态机状态

**`messages` + `tasks`**，完整描述状态机当前所处的一切。

**messages：** 完整消息流，状态机恢复的原材料。

**tasks：** 结构化任务，有独立生命周期：

```
created → in_progress → blocked → resolved / failed / cancelled
```

**双向锁：**
- `blocked_by` — 谁在阻塞我（我依赖谁）
- `blocking` — 我在阻塞谁（谁依赖我）
- 父 task 等子 task = 父 blocked_by 子，子 blocking 父

**级联释放：**
- task 完成 → 沿 `blocking` 链唤醒所有被阻塞的 task
- task 取消 → 沿 `blocked_by` 链级联取消所有依赖 task
- 节点离线 → Bus 广播 `node_offline` → Engine 收到后对该节点相关的所有 task 级联释放 → 注入显式的失败通知消息
- 释放通知不是静默的——Agent 会收到一条不可忽略的系统消息，知道自己等不到了

---

### 5. MCP — 资源管理与执行

**一个 MCP 实例 = 一个 namespace = Bus 上一个节点。** Engine 只和 `mcp/{namespace}` 通讯，对本地和远程节点无区别。

**两种节点类型**：

| | LocalMcpNode | RemoteMcpNode |
|---|---|---|
| 构造 | `new(namespace, root_dir)` | `new(namespace, RemoteConfig)` |
| 发现 | `DiscoveryModule::scan(root_dir)` — `{root}/tools/*/tool.toml` + `{root}/skills/*/SKILL.md` | HTTP `tools/list` |
| 执行 | ScriptTool subprocess (stdin/stdout JSON) | HTTP `tools/call` 代理 |
| Skill | ✅ `skills/*/SKILL.md` 渐进披露 L1→L2→L3 | ❌ |

**框架只提供机制，不内置任何 Tool。** 所有本地 Tool 通过文件夹约定发现——`tool.toml` 声明元数据（name、description、runtime、entrypoint、params_schema），`ScriptTool` 包裹入口脚本通过 stdin/stdout JSON 协议执行。支持 Python / Bash / Rust 三种 runtime。Skill 同理——`skills/{name}/SKILL.md` YAML frontmatter + Markdown body。

**DAG 执行**：Engine 发 `tool_call_set`（含双向锁 blocked_by/blocking）→ MCP 环检测 → 拓扑排序 → 分层并发 → 失败沿 blocking 级联取消 → 返回 `tool_result_set`。

**多 namespace 隔离**：`mcp/filesystem/read_file` ≠ `mcp/network/read_file`。同一 namespace 内 name 冲突 → panic（开发期错误）。

**MCP 不感知 Agent / Engine / ModelMessage**——MCP 只产出 `ToolResultItem`（纯数据 struct 含 call_id、name、status、result、error），由 ModelAdapter 负责转换为模型 API 格式。

---

### 6. ModelAdapter — 模型格式适配

**职责：框架内部消息 ↔ 外部 API 格式。** 同时负责 MCP 工具结果 → 模型消息的转换。

**模型调用方向**：
- 监听 Bus 上的 `model_call` 消息
- 将框架内部标准消息格式转换为各供应商 API 格式（OpenAI / DeepSeek / Anthropic 等）
- 发出 `model_response` 消息回到 Bus（含 text + tool_calls + usage）
- **LLM / VLM 统一适配**——对话模型和多模态模型走同一套消息格式，Adapter 负责差异
- 可插拔——新增供应商只需新增一个 Adapter，不影响任何其他组件

**工具结果转换**（Phase 5 集成）：
- `tool_result_to_model_message(&ToolResultItem) -> ModelMessage` — MCP → 模型格式的唯一转换入口
- MCP 产出纯数据 `ToolResultItem { call_id, name, status, result, error }`，ModelAdapter 按 status 决定 content 格式：
  - `"success"` → `result.to_string()` 直接作为 content
  - `"error"` / `"cancelled"` → 包装为 `{"error": "..."}`
- 依赖方向：`arf-model-adapter → arf-mcp`，单向。MCP 不感知 ModelMessage

## 与 v0.x 的关键差异

| | v0.x（当前，已归档） | v1.x（设计） |
|---|---|---|
| **耦合方式** | Engine 直接持有 MCP/Memory/Plugin 引用 | 全部通过 Bus 消息解耦 |
| **Agent 感知** | Agent 暴露 `wait()` / `finish_wait()` | Agent 不知道 park/resume，Engine 管理 |
| **State** | `messages: list` + `waiting: dict` 扁平结构 | `messages` + `tasks` 有生命周期 + 双向锁 |
| **A2A** | Subagents + Teammates 两套独立模式 | 统一 Bus，peer message = `to=sid` 的定向消息 |
| **可观测性** | TracePlugin 插桩，事后 JSONL | Bus 上一切消息天然 trace，实时可见 |
| **错误通知** | 静默挂起，pending 无反馈 | 级联释放时 Engine 注入显式通知消息 |
| **资源发现** | FileWatcher 轮询文件系统 | Bus 广播 `node_online`，零延迟 push |
| **MCP** | Engine 直接持有 MCP 引用 | 独立 Bus 节点，每个 namespace 一个节点，LocalMcpNode（文件夹扫描）+ RemoteMcpNode（HTTP 代理） |
| **Tool 注册** | 内置 Tool + API 注册 | 文件夹约定：`{root}/tools/*/tool.toml` 扫描发现，框架不内置任何 Tool |
| **MCP↔ModelAdapter** | 直接方法调用 | ModelAdapter 持有 `tool_result_to_model_message()` 转换函数，MCP 只产出纯数据 |
| **实现语言** | Python | 核心（Bus / AgentConfig / State / Engine）用 Rust，Python PyO3 绑定 |
