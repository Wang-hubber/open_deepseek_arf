## 1. Purpose

This document describes the threat model and security controls for ARFV1's Backend abstraction (Phase 11 / G-01). It is intended for:
- Application developers choosing a backend
- Security reviewers evaluating ARF deployments
- Future contributors adding new backends

ARFV1's backend abstraction introduces a unified surface (`BackendProtocol`) through which LLM-generated tool calls interact with persistent state. This document enumerates the threats that surface and the controls in place.

---

## 2. Scope

### In scope

- `BackendProtocol` trait surface (ls / read / write / edit / delete / glob / grep / upload_files)
- `SandboxBackendProtocol` extension (id + execute)
- Three primary backends: `StateBackend`, `FilesystemBackend`, `LocalShellBackend`
- `CompositeBackend` (path-prefix routing)
- `BackendFactory` (env-driven construction)
- `FilesystemMiddleware` / `MemoryMiddleware` (model-side tool injection)

### Out of scope

- Network security (TLS, API keys) — covered by Provider config
- Auth/authorization at the LLM API layer — out of band
- Denial-of-service at the model API layer — Provider-level concern

## 3. Assets

| Asset | Sensitivity | Storage |
|-------|-------------|---------|
| User prompts | High | In-memory (`State.messages`) |
| Tool call results | High | In-memory + Trace JSONL |
| File system contents (under backend root) | Variable | Host FS via FilesystemBackend |
| Memory files (AGENTS.md) | Medium | Backend (typically FS) |
| Persistent memory | High | Backend (writes via MemoryMiddleware v2) |
| Host shell environment | Critical | Host OS via LocalShellBackend |
| BackendError messages | Low | Returned to LLM |
| Trace events | Medium | SessionStore (sqlite/jsonl) |

## 4. Threats

### T1: Path traversal (escape sandbox root)

**Description**: A model-generated `read("/../etc/passwd")` could escape the sandbox root if path validation is incomplete.

**Affected**: `FilesystemBackend`, `LocalShellBackend` (via FS delegation)

**Controls**:
1. `BackendPath::new()` rejects `..` components at construction (`crates/arf-backend/src/path.rs:25-50`).
2. `FilesystemBackend::resolve()` calls `fs::canonicalize()` and verifies the result starts with the canonicalized root (`crates/arf-backend/src/filesystem.rs:46-70`).
3. Symlinks pointing outside root are detected via canonicalize and rejected.
4. Two-layer defense: BackendPath (type-level) + resolve() (runtime).

**Residual risk**: Low. Both layers must fail for an escape.

### T2: Symlink-based escape

**Description**: A symlink inside the sandbox root pointing to `/etc/passwd` could be followed by naive `fs::read`, reading host files.

**Affected**: `FilesystemBackend`

**Controls**:
1. `FilesystemBackend::read()` checks `meta.file_type().is_symlink()` and returns `BackendError::PermissionDenied` (`crates/arf-backend/src/filesystem.rs:117-122`).
2. `resolve()` uses `fs::canonicalize()` which dereferences symlinks; if the target is outside root, the comparison fails.

**Residual risk**: Low. Symlinks are explicitly not followed for reads.

### T3: Arbitrary shell execution

**Description**: `LocalShellBackend::execute("rm -rf /")` could destroy the host.

**Affected**: `LocalShellBackend`

**Controls**:
1. **Opt-in only** — `LocalShellBackend::new()` requires explicit choice; default is `StateBackend`.
2. **CWD confinement** — `cmd.current_dir(&self.cwd)` (`crates/arf-backend/src/local_shell.rs:99-104`).
3. **Timeout** — `tokio::time::timeout` with default 30s (`crates/arf-backend/src/local_shell.rs:106-114`).
4. **Output cap** — 1MB default truncation (`crates/arf-backend/src/local_shell.rs:115-122`).
5. **Path escape prevention** — File ops via FilesystemBackend::resolve() still enforce sandbox.

**Residual risk**: Medium. A malicious prompt can still execute arbitrary shell commands within the cwd. **Application-level sandboxing** (Docker, nsjail, Firecracker) is recommended for untrusted inputs.

### T4: Denial of service via large files

**Description**: `write("/huge", 10GB)` could exhaust memory.

**Affected**: `FilesystemBackend`, `LocalShellBackend`

**Controls**:
1. FilesystemBackend delegates to `tokio::fs::write` which writes incrementally (not buffered).
2. LocalShellBackend's output cap (1MB) prevents execute() from returning GBs of output.
3. **No** explicit size limit on write — application responsibility.

**Residual risk**: Medium. Application should enforce size limits if needed.

### T5: Denial of service via grep / glob

**Description**: `grep(".*", path="/")` on a large directory tree could run for minutes.

**Affected**: `FilesystemBackend`, `LocalShellBackend`

**Controls**:
1. `FilesystemBackend::grep()` uses `regex::Regex::is_match()` per line, bounded by file size.
2. `walkdir` walks the tree but doesn't follow symlinks (bounded by sandbox root).
3. **No** explicit timeout — application should set per-tool timeouts via `EngineConfig.tool_timeout_ms` (default 30s).

**Residual risk**: Medium. Engine-level timeout is the main mitigation.

### T6: Edit ambiguity exploitation

**Description**: `edit("/file", old="x", new="rm -rf /")` could be triggered by a model with insufficient context, modifying critical files.

**Affected**: `BackendProtocol.edit` (all backends)

**Controls**:
1. `edit()` requires `old_string` to match uniquely (or `replace_all=true`).
2. Application-level: use `ToolPermission::Ask` for sensitive files.
3. **FilesystemMiddleware** uses `FilesystemMiddleware::deny("write_file")` to opt out of write.

**Residual risk**: Low for read-only backends (StateBackend). Medium for FS/Shell backends with write access.

### T7: Tool message prompt injection via filesystem content

**Description**: A file with adversarial content ("Ignore previous instructions...") could be read by the model and treated as instructions.

**Affected**: All backends; affects LLM behavior, not ARF directly.

**Controls**:
1. ARF does not interpret file content as instructions; the LLM does.
2. **Application responsibility** — system prompt should instruct model to treat file content as data, not instructions.
3. Output truncation (1MB cap on LocalShellBackend) limits context window saturation.

**Residual risk**: Inherent to LLM architecture. Cannot be eliminated by ARF alone.

### T8: Cross-backend contamination (CompositeBackend routing)

**Description**: `CompositeBackend` routes by path prefix. A file written to `/memory/foo` via StateBackend could be read via a different prefix if routing changes.

**Affected**: `CompositeBackend`

**Controls**:
1. Longest-prefix matching (`crates/arf-backend/src/composite.rs:53-65`) ensures consistent routing.
2. Default fallback for unmatched paths is explicit (`crates/arf-backend/src/composite.rs:67`).
3. Path translation preserves path semantics (`crates/arf-backend/src/composite.rs:55-64`).

**Residual risk**: Low. Routing is deterministic.

### T9: Environment variable injection

**Description**: `ARF_BACKEND=redis` (unknown type) could be parsed as a malicious backend.

**Affected**: `BackendFactory::from_env`

**Controls**:
1. Unknown backend types return `BackendError::Other` (`crates/arf-backend/src/factory.rs:60-65`).
2. Default `unset → StateBackend` (safe default).
3. Filesystem path validation in `FilesystemBackend::new()` rejects relative/invalid paths.

**Residual risk**: Low.

### T10: BackendError information leakage

**Description**: Error messages could leak sensitive paths or internal state to the model.

**Affected**: All backends

**Controls**:
1. `BackendError` variants include path but not content.
2. Normalized error codes (`file_not_found`, `permission_denied`) provide consistent LLM-facing messages.
3. Internal details (full path, syscall errors) wrapped in `BackendError::Io(msg)`.

**Residual risk**: Low. Errors expose path strings but not file contents.

## 5. Trust Model

### Trusted

- Application code (provides `AgentConfig`)
- LLM API responses (treated as untrusted below)
- `EngineConfig` (set at build time, not mutated by model)

### Untrusted

- LLM-generated tool calls (params, paths, content)
- LLM-generated text in tool results (read from FS, may contain adversarial instructions)
- File system contents (read via backend)
- Shell command output (from LocalShellBackend)

### Boundary

The Engine is the trust boundary. All LLM outputs pass through:
1. JSON parsing (type validation)
2. Tool permission check (`ToolPermission`)
3. Backend call (with sandbox controls)
4. Result truncation

The Backend is the secondary boundary. It enforces:
1. Path sandboxing (canonicalize + prefix check)
2. Symlink refusal
3. (LocalShellBackend) CWD + timeout + output cap

## 6. Security Controls Summary

| Control | Backend | Threat mitigated |
|---------|---------|------------------|
| `BackendPath::new()` rejects `..` | All | T1 |
| `FilesystemBackend::resolve()` canonicalize | Filesystem, LocalShell | T1, T2 |
| Symlink refusal in `read()` | Filesystem, LocalShell | T2 |
| `LocalShellBackend` opt-in only | LocalShell | T3 |
| CWD confinement (`cmd.current_dir`) | LocalShell | T3 |
| Timeout (`tokio::time::timeout`) | LocalShell | T3, T5 |
| Output cap (1MB) | LocalShell | T3, T4, T7 |
| Longest-prefix routing | Composite | T8 |
| Unknown backend → Error | Factory | T9 |
| `BackendError::code()` normalization | All | T10 |
| `ToolPermission` (Ask / Deny) | Engine-level | T6 |
| `EngineConfig.tool_timeout_ms` (30s) | Engine-level | T5 |

## 7. Recommendations for Application Developers

### Default: Use StateBackend

For untrusted prompts (e.g., from user input), start with `StateBackend` (Phase 10 G-04). It provides:
- No host FS access
- No shell execution
- Process-isolated state

```rust
let backend = BackendFactory::default_backend(); // StateBackend
```

### Production: Use CompositeBackend

For production apps, use `CompositeBackend` with:
- `/memory/*` → `StateBackend` (transient state)
- `/workspace/*` → `FilesystemBackend` rooted at user's project dir
- default → `StateBackend`

### Untrusted shell: Use LocalShellBackend with caution

`LocalShellBackend` exposes host shell. Recommended for:
- Trusted developer environments
- Sandboxed deployments (Docker, VM)

For untrusted prompts, do NOT use `LocalShellBackend`. Use `StateBackend` only.

### Audit

For security review:
- Trace all `execute()` calls in trace JSONL
- Monitor `BackendError::PermissionDenied` events (path escape attempts)
- Set `tool_timeout_ms` to a value appropriate for your workload

---

## 8. Out-of-Band Mitigations

These are **application-level** controls not provided by ARF:

1. **Container isolation** — Run ARF agents in Docker / nsjail / Firecracker
2. **Resource limits** — cgroup memory + CPU limits
3. **Network policies** — Restrict outbound traffic to LLM API only
4. **API key scope** — Use minimum-privilege LLM API keys
5. **Audit logging** — Forward trace events to a SIEM
6. **Rate limiting** — Per-session token budget
