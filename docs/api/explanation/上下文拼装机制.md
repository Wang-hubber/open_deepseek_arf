# 上下文拼装机制 — 为什么 Engine 不再把 skills 烘焙进 system_prompt

> 💭 Diátaxis 桶位：**Explanation**（设计哲学 / 关键决策背后的"为什么"）

## 一句话总结

ARF Engine 在 `do_model_turn` 时按 **4 层独立 system message + 对话** 拼装发给模型的 messages 列表。每层有独立的稳定性等级 — 拼装顺序就是为了让**最长前缀保持稳定**，让 LLM provider 的 prompt cache 命中率最大化。

## 4 层模型

```
[0]    system:  system_prompt_template        (build-time 固定，**最稳定**)
[1..N] system:  initial_memory[i]             (build-time 固定，**会话内稳定**)
[N+1]  system:  skills (现采 BusGraph)        (**低频变化** — 节点上下线时变)
[N+2..] user/assistant/tool                 (对话 — 每次 turn 增长)
```

| 层级 | 字段 | 变更频率 | 失效时影响 |
|---|---|---|---|
| 0 | `system_prompt_template` | build 后永不变 | 永远 0 cost（不会变） |
| 1..N | `initial_memory` (Vec) | build 后永不变 | 永远 0 cost |
| N+1 | skills (现采) | 节点上下线 / 迁移 / scale | 只失效这一段；前缀 [0..N] 仍命中 |
| N+2.. | conversation | 每 turn +1~2 | 高频变，但只影响尾部 |

`state.messages` 内部**只存对话**（user / assistant / tool），不存 system prefix。Engine 在 `do_model_turn` 把 prefix 拼到 `state.messages` 前面，构成本轮的 `model_call.messages`。

## 为什么不再 `{{skills}}` 替换

**历史设计（v0.x）**：在 `EngineBuilder.build` 时把 `{{skills}}` 替换成 skills 文本，烘焙进 `system_prompt: String`，整段随 build 冻结。

**问题**：
1. **Prompt cache 命中率低**：任何 skill 节点上下线（不算低频 — reconnect、scale、节点迁移都会变）→ 替换内容变化 → **整段 system_prompt 变化** → cache miss
2. **状态陈旧**：build 一次后冻结，session 期间不更新；ch2 改本地 tool 列表时 system_prompt 不会刷新
3. **`initial_memory` 未实现**：`AgentConfig.initial_memory: Vec<String>` 是死字段，Engine 从来不读

**修复（2026-07-02）**：`system_prompt_template` **保持原样发送**（不再替换占位符）；Engine 在 `do_model_turn` 现采 BusGraph 的 `kind=skill` 节点，作为独立 system message 注入；`initial_memory` 真正接进来，每条作为独立 system message。

## Skills 现采 + Hash 缓存

```rust
pub(crate) fn collect_skills_cached(
    primary_bus: &Arc<arf_bus::Bus>,
    cache: &std::sync::Mutex<(u64, String)>,
) -> String {
    let graph = primary_bus.graph();
    let mut skill_ids: Vec<String> = graph.nodes.iter()
        .filter(|n| n.capabilities.get("kind").and_then(|v| v.as_str()) == Some("skill"))
        .map(|n| n.node_id.to_string())
        .collect();
    skill_ids.sort();
    skill_ids.dedup();
    let hash = fold_over_bytes(&skill_ids);
    let mut guard = cache.lock().unwrap();
    if guard.0 == hash && !guard.1.is_empty() {
        return guard.1.clone();
    }
    // 重新收集 + 写回缓存
    let content = format!("Available skills:\n{}", skill_ids.iter().map(|s| format!("- {s}")).join("\n"));
    *guard = (hash, content.clone());
    content
}
```

**关键点**：
- **空集合返回空串**：调用方在 skills 为空时**不推送**空 system message（否则会顶开 cache 边界）
- **稳定排序**：`(u64, String)` 缓存键基于排序后去重的 node_id 列表字节 fold，节点集合相同 → 同一文本 → cache 命中
- **节点变化才重发**：skill 节点 offline / online 触发 hash miss，content 重写，前缀 [0..N] 仍命中

## Prompt cache 视角的稳定前缀

考虑连续两轮 ReAct，skills 没变：

```
Turn 1 messages: [
  system: "你是一个助手",                          # [0] 永久命中
  system: "fact-1",                                # [1] 永久命中
  system: "Available skills:\n- mcp/skill/a",      # [2] 本次命中（hash 命中）
  user: "现在几点？",                                # [3] 新
  assistant: tool_call(get_time)                   # [4] 新
  tool: "2026-07-02 14:00:00",                      # [5] 新
  assistant: "当前北京时间 14:00"                   # [6] 新
]

Turn 2 messages: [
  system: "你是一个助手",                          # [0] 永久命中
  system: "fact-1",                                # [1] 永久命中
  system: "Available skills:\n- mcp/skill/a",      # [2] 本次命中（同 hash）
  user: "那上海呢？",                                # [3] 新
  ...
]
```

provider 的 prompt cache（OpenAI 1h / Anthropic 5min / DeepSeek 缓存）按 prefix 字节匹配，**前 3 条 system 消息**在前缀 [0..hash_length) 字节完全一致 → cache hit。Skills 变也只会让 hash 之后的内容变，前 3 条的前缀匹配（直到被替换点）继续命中。

## 不变量 & 限制

- **`Engine::system_prompt()` getter 返回的是 `system_prompt_template` 原样**（不替换 `{{skills}}`，因为现在不替换了）
- **`state.messages[0]` 现在是 user**（不再是 system）— 旧版断言会破；如果 App / 测试在直接读 `state.messages[0]`，需要相应更新
- **多 bus Agent 暂只查 primary_bus**：`collect_skills_cached` 用 `self.primary_bus.graph()`，跨 bus skills 不会自动并入（未来扩展）
- **`{{skills}}` 占位符语义变化**：v0.x 替换 / v1.x 原样发送。放入模板的 `{{skills}}` 文本会原样出现在 messages 里 — 不报错，只是无效

## API 影响

| API | 行为变化 |
|---|---|
| `EngineBuilder::build(config)` | 不再校验 `{{skills}}` 占位符；无 skill 节点时 build 成功，placeholder 留在 template 里 |
| `Engine::system_prompt()` | 返回 template 原样 |
| `Engine::do_model_turn` | 内部按 [template, *memory, skills, *state.messages] 拼装 |
| `state.messages` 含义 | 仅存对话（user/assistant/tool），不含 system prefix |
| `Engine::run` | 行为不变 — 观察者看到的是同一份 LLM 请求 |
| `ModelCall.tools` | 仍由 `collect_tools_from_routes` 注入（commit d0f1853） |

## 验证方式

最直观的检查 — 在 `do_model_turn` 调试点打印 `state.messages` 和拼装后的 `model_call.payload.messages`：

```python
# 在 tutorial 代码里临时加：
import json
print("state.messages:", json.dumps(state.messages, ensure_ascii=False))
# 你会看到：
# state.messages: [{"role": "user", "content": "..."}, {"role": "assistant", ...}]
# 没有 system — 这就是新的不变量
```

如果想看完整发给模型的 messages（含 prefix），可以在 `do_model_turn` 入口处 `eprintln!` 一下 payload，或用 `mc-trace` 之类的 trace 节点订阅 `model_call` 消息。
